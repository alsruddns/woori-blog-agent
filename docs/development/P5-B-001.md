## Finding: the 12 versions were test fixtures

The operations database was queried in `READ ONLY` transactions. The 348-row checkpoint corresponds to the content count through 2026-10-27 13:20:28 KST. Four later executions of `services/api/tests/test_integration.py::test_content_versions_and_lease_recovery` each persisted the test's three hard-coded fixture versions (`original`, `localized`, `revised`), at 13:53:05, 13:56:15, 13:58:58 and 14:03:29 KST. This accounts for exactly 12 rows and the current count of 360.

The fixture inserts the three versions and an already-expired `diagnostic` job in one database transaction. The matching job's `created_at` is identical to the three version rows; `worker.tick()` then writes `run.failed` with `LeaseExpired`. Four adjacent integration runs each have `run.queued`, `run.started`, `run.completed`. These rows are test-worker diagnostics, not content-generation jobs: no `generation_jobs` row links to these runs. The content table has no actor, request path, or run-id columns, and there is no `content.version.created` event for these direct SQL inserts. The source test has no user/API editor request; its SQL fixture exactly matches the stored values. This is a test-isolation defect, not an automatic content retry or an editor idempotency defect. The synthetic lease fixture's `attempts=3` represents its intentional terminal lease-recovery case; it did not retry the content inserts.

## Isolation change

The integration tests previously opened independently committed `connection()` contexts against the normal operations `DATABASE_URL`. A new `rollback_lab` fixture now shares one connection across the FastAPI route and Worker, wraps each call in savepoints under an outer forced-rollback transaction, and compares persisted `content_versions` and `audit_events` counts before and after teardown. The same fixture covers test helper database access. The targeted two-test run passed, and the persisted operations counts stayed at 360 versions and 1,305 audit events.

Configuration paths were checked without printing credentials: `.env` uses `woori_app` and `woori_blog_agent`; `.env.evaluation-readonly` uses `woori_eval_reader` and `woori_blog_agent_eval`; `.env.migration` targets only the operations database; `.env.evaluation-migration` targets only the evaluation database. Both DBs are distinct. On the operations database, `woori_app` has no content-version UPDATE/DELETE privilege and immutable triggers reject UPDATE/DELETE/TRUNCATE for content versions and audit events. On the evaluation database, `woori_eval_reader` has SELECT only and no INSERT/UPDATE/audit INSERT privilege. Evaluation owner credentials are not used by normal API settings. The full test suite uses rollback fixtures for database-backed synthetic writes; the previously unisolated integration test was the discovered exception and is now covered by an explicit post-rollback assertion.
