# P5-UI-002 — Dashboard 브라우저 검증 및 수집 데이터 연결 점검

작성일: 2026-10-28 (KST)
브랜치: `develop`
검증 기준 HEAD: `b59726e72b77ea2789d2d030a61db352eb031831`

## 목적

P5-UI-001에서 구현한 콘텐츠 운영 화면을 실제 Chromium 브라우저로 검증하고, 트렌드 데이터가 0건으로 표시되던 원인을 확인했다. 운영 DB와 격리 DB를 합치거나 복사하지 않았으며 운영 DB에 마이그레이션을 적용하지 않았다.

## 데이터 연결 원인 및 현재 수량

- 운영 DB `woori_blog_agent`는 `woori_app`으로 조회했다. 스키마 버전은 별도 migration 계정의 읽기 전용 연결로 34를 확인했다. `content_versions` 360건, `audit_events` 1,422건, `publication_approval_events` 0건이며 `trend_observations` 테이블은 없다.
- 격리 테스트 DB `woori_blog_agent_test`는 `woori_test_app`으로 조회했다. 스키마 39이며 트렌드 관측값 60건이 유지되어 있다: HK/JP/KR/SG/TW/US 각각 10건.
- 평가 DB `woori_blog_agent_eval`의 `woori_eval_reader` 연결에서 원고 버전 260건, 품질 평가 71건, 모델 실험 평가 36건, 생성 결과 29건을 확인했다.
- 36개 모델 실험 평가는 모두 `local / Qwen3-4B-Q4_K_M.gguf`였다. NVIDIA Build 비교 결과는 DB에 없어 화면에서 만들어내지 않았다.
- Dashboard 개발 검증은 기존처럼 운영 DB를 기본으로 선택하면 트렌드가 0건이다. 테스트 환경에서 명시적으로 `woori_blog_agent_test`를 연결하면 60건을 조회한다. 서로 다른 DB의 데이터는 합치거나 복사하지 않았다.
- 모델 비교 화면은 원래 운영 DB 연결을 사용해 평가 DB에만 있던 36건을 보지 못했다. 읽기 API를 `EVALUATION_DATABASE_URL`의 `woori_eval_reader` 전용 연결로 바꾸고 DB명·계정 식별을 확인하도록 했다. 테스트에는 해당 계정이 실제 평가 DB에만 연결되는지와 상세 조회가 평가 DB에서 이루어지는지 포함했다.
- 평가 화면 조회를 위해 격리 평가 DB의 읽기 역할에 `research_experiment_evaluations` SELECT 권한을 추가했다. 기존 `article_quality_evaluations` SELECT와 함께 필요한 두 테이블만 읽을 수 있다. 변경은 평가 DB 감사 이벤트 `evaluation.reader_access.granted` (ID 85084)에 기록됐다. 운영 DB 권한과 스키마는 변경하지 않았다.

## 구현 및 브라우저 검증

- 원고 그리드에 페이지당 10/25/50개 선택을 추가했다. 페이지 크기 변경은 1페이지로 돌아가고 서버 페이지네이션으로 요청한다.
- 원고 목록·상세 및 수집 자료 조회 오류에는 내부 네트워크 오류 대신 한국어 안내를 표시한다.
- Playwright 1.64.1을 개발 의존성으로 추가했다. 브라우저는 이미 로컬에 설치된 Chromium을 사용했으며 새 브라우저나 모델을 내려받지 않았다. 실행 구성은 데스크톱 1440×1000 및 모바일 390×844다.
- 임시 API `127.0.0.1:18100`, Dashboard `127.0.0.1:13100`를 사용했다. API는 테스트 DB와 평가 읽기 전용 DB를 분리해 연결했고 `PGOPTIONS=default_transaction_read_only`를 적용했다. 임시 서버는 테스트 후 Ctrl+C로 정상 종료했다. 3100/8100 운영 포트와 llama.cpp 11435는 건드리지 않았다.
- Playwright 결과: 데스크톱 5건과 모바일 5건, 총 10건 통과. 원고 18건 표시, 언어 필터, 10개 페이지네이션(2페이지 8건), 행 선택 후 상세 지연 조회, 저장 본문 미리보기, 4개 상세 탭, Esc 닫기 및 포커스 복귀를 확인했다. 이 중 기존 원고는 `review_actions_allowed=false`, `publish_ready=false`로 반환되어 UI에서 검토·발행 권한이 열리지 않았다.
- 수집 화면에서 60건과 JP 지역 필터(10건)를 확인했고 상세 출처 링크를 열었다. 모델 비교 화면에서 평가 기록 36건을 표시했다. `/operations`와 `/research` 호환 경로도 확인했으며 `/research`는 `/manuscripts`로 이동한다. 의도적으로 중단한 원고 목록 요청은 접근 가능한 오류 메시지로 표시됐다.
- 모바일에서 상세 시트 너비 380px 이상 및 문서 가로 오버플로 없음, 데스크톱에서 목록과 상세 시트 및 주요 운영 화면을 확인했다.

## 비밀정보, 운영 보호 및 한계

- `scripts/verify-secrets.py`를 임시 Dashboard 실행 중 수행했고 응답·저장 이력·발행 정책 검사가 통과했다. `/research`의 정상 307 호환 리디렉션을 따라 최종 `/manuscripts` 화면을 검사하도록 고쳤다.
- 첫 검사에서 짧은 4자 DB 비밀번호가 상태 응답의 일반 문장 일부와 일치하는 오탐이 있었다. 긴 비밀값은 기존 정확 일치 검사를 유지하고, HTTP 응답 내 짧은 값은 자격 증명 필드나 PostgreSQL URL 문맥에 실제로 등장할 때 탐지하도록 분리했다. `test_short_secret_uuid_collision_does_not_hide_plaintext` 회귀 검사를 추가했다. 비밀값은 출력하거나 기록하지 않았다.
- 실제 운영 DB 조회에서 마지막 감사 이벤트는 기존 `operations.backup.warning`(2026-10-28 03:00 KST)이었다. 이 작업은 운영 DB를 읽기만 했으며 운영 콘텐츠·감사 이벤트 쓰기 및 migration은 하지 않았다.
- Blogger 요청, 유료 API, AI 추론은 0회다. HTTP 및 E2E 검증은 로컬 격리 환경에서만 수행했다.
- 승인·검토 쓰기 흐름은 이번 브라우저 시나리오에서 실행하지 않았다. 기존 원고에 대해 권한이 차단된 상태와 화면 노출만 확인했다. 실서비스 3100/8100 서버에서의 운영 DB UI 검증도 수행하지 않았다.
