- **Work time:** 2026-11-18, Asia/Seoul
- **Reason:** The operator requested applying the Worker after manual and automatic publication controls showed "Worker application pending or connection failed".
- **Existing problem:** Publication Worker repeatedly reported SQLSTATE 42883 (`UndefinedFunction`) and a `degraded` heartbeat. It had read controls revision 29, but the Automation UI correctly treated publication controls as unapplied. The safe diagnostic identified `trends_publication.py:533:enqueue_trends_auto_jobs` and the mismatched operator types `text = timestamp with time zone`.
- **Purpose:** Fix the Trends enqueue query's positional parameter mismatch, retain safe error diagnostics, and apply the corrected Worker while preserving all publication gates.
- **Before:** Candidate SQL placeholders were ordered `(blog_id, received_after, contract_blog_id, contract_language)`, but Python supplied `(blog_id, contract_blog_id, contract_language, received_after)`. PostgreSQL therefore compared the JSON target-language text with the activation timestamp, and every Worker cycle failed before publication policy application.
- **After:** Reordered the parameters to `(blog_id, trends_auto_enabled_at, contract_blog_id, language_code)` and added a regression assertion to the Trends enqueue fake-connection test. Added `safe_database_error_hint()` and `safe_database_error_site()` to log only a redacted type/operator signature and application file/line/function; SQL, parameters, and quoted values are omitted. Publication Worker PID `38964` now runs commit `76928c8` in `scheduled-auto-manual-trends` mode with a fresh `running` heartbeat. Controls revision 29 is acknowledged and `policy_applied=true`; the live Operations API returns HTTP 200 and reports manual, global auto, and Trends auto as normal. After the fix, a Trends Auto job (`683ca5a1-c728-4734-9828-3540ae9ab2ae`) published successfully with Blogger readback verification. The local Trends backoff was inactive at final verification. No API process was stopped because the verified API process tree still had established clients; Worker was gracefully stopped and restarted independently, with no force termination.
