# P5-CODEX-160 — Graceful background service reflection and login startup

- **Work ID:** P5-CODEX-160
- **Work time:** 2026-11-18, Asia/Seoul
- **PostgreSQL audit:** `agent.p5_codex_160.started` ID `723251` (`woori_blog_agent`, `woori_app`); completion event will be appended after service and task verification.
- **Reason:** The operator reported that the API and Dashboard were running in the background and could not be stopped from their original terminals, preventing the verified P5-CODEX-159 changes from being reflected. The existing Windows login task also omitted the Trends-capable Publication Worker mode.
- **Existing problem:** `stop.ps1` refused any API/Dashboard process without a manifest-owned runner even when its exact checkout process had a matching local identity file and a cooperative stop channel. The login task could point to `start-services.ps1` but still launch its default `manual-confirmed` mode.
- **Purpose:** Safely request graceful shutdown from verified background API/Dashboard processes and have the owned hidden logon task start API, Dashboard, Research Worker, and Publication Worker in the explicitly configured Trends-capable mode.
- **Before:** Runtime reflection stopped at unmanaged API/Dashboard PIDs; the auto-start action had no `-PublicationMode` argument.
- **After (implementation):** Unmanaged HTTP services are stoppable only when the listener PID maps to the exact project entrypoint, its identity file matches PID/service/checkout/instance, Windows owner is the current user, and established connections are zero. Shutdown uses the existing local identity-bound stop request and waits; no process termination fallback was added. The project-owned logon task's action now explicitly passes `-PublicationMode scheduled-auto-manual-trends`; install repairs an older project action while preserving its trigger, principal, and retry settings. All four services remain hidden/background processes, start after interactive user logon, and retain database/operator publication gates.
