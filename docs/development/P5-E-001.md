## 시작 상태와 운영 DB 보존

시작 시 `develop`과 `origin/develop`은 같은 커밋이었고 작업 트리는 깨끗했다. `main`은 `96c7ae5d23f48db0774066a87a8f3259f9c20c97`에 머물렀다.

3100 포트는 PID 37740 (`node.exe`, 프로젝트의 `next start`)이, 8100 포트는 PID 32432 (`python.exe`, 프로젝트 venv의 Uvicorn)가 점유 중이었다. 각각 상위 프로세스는 24676 `cmd.exe`, 18992 프로젝트 Python이다. 두 서비스는 `.runtime/servers.json` 관리 기록에 없고 원래 터미널의 정상 종료 제어도 확인할 수 없어 종료 스크립트 정책상 전환할 수 없다. 강제 종료하지 않았고 기본 포트에서 최신 버전을 시작하지 않았다. 이 Phase의 재확인 시 established TCP 연결은 없었지만, 연결 부재가 정상 종료 승인이나 프로세스 소유권 기록을 대신하지는 않는다. 프로젝트 llama.cpp PID 39500 및 11435 포트도 수정하거나 종료하지 않았다.

## 백업 및 Migration 033

새 운영 백업 `backups/20261027T062250Z.dump` (421,563 bytes)을 생성했다. `pg_restore --list`에서 PostgreSQL custom-format 아카이브 카탈로그를 읽을 수 있음을 확인했다. SHA-256: `C4D343010C89DAA3DB7B2F3B0C58B5889B89573D33FD07789ABC1E6CFB70BEC2`. 이 새 백업 자체에 대한 복원 리허설은 이번 Phase에서 수행하지 않았다. 앞선 Phase 5-D 복원 리허설은 별도 격리 DB에서 성공했다.

Migration 033은 기존 API/Dashboard 세션이 3100/8100에서 계속 실행 중이고 원래 터미널에서 graceful shutdown을 확인할 수 없어 운영 DB에 적용하지 않았다. 실행 중 API를 둔 채 운영 스키마를 변경하면 안 된다는 운영 절차가 적용된다. 테스트 DB에는 동일 마이그레이션이 적용되어 있고 스키마 33이며 `publication_approval_events` 테이블과 권한은 테스트 및 전체 통합 검증 대상이다. 운영 Migration 033은 유지보수 중단, 복구 가능한 백업 검증 및 운영자 유지보수 창 확인 후 별도 실행해야 한다.

## 최신 코드의 격리 실행과 UI 범위

최신 develop API를 `127.0.0.1:18100`, Dashboard를 `127.0.0.1:13100`에서 테스트 DB에 연결해 실행한 뒤 정상 종료했다. API `/health`, 인증된 `/admin/research/state`, `/admin/publications`, Dashboard `/research`, 같은 출처 `/api/research/state`가 성공했다. 연구 상태 응답에 Phase 5-D 편집 버전 및 승인 이력 필드가 포함됐다. 발행 상태는 `adapter_available=fake_only`, `real_writes_enabled=false`, `publish_ready_enabled=false`였다. 빈 테스트 DB에서는 원고 후보·Mock 작업이 0건이었다. 최신 UI가 테스트 DB의 운영 콘텐츠처럼 보이지 않도록 운영 자료를 복제하지 않았다.

현재 3100의 `/research`는 HTTP 200을 반환하지만, 8100의 상태 응답에는 `article_editorial_versions`와 `publication_approval_events`가 없었다. 그러므로 기본 포트 서비스는 최신 코드가 아니다. 최신 코드의 `/research` HTML과 BFF 데이터 경로는 격리 포트에서 HTTP 검증했으나 Windows 브라우저 인벤토리에서 제어 가능한 브라우저 surface가 반환되지 않아 브라우저 클릭, 입력, 편집 저장 UI는 검증하지 않았다. 편집/승인 쓰기 동작은 브라우저가 아닌 격리 테스트 DB를 쓰는 FastAPI TestClient 회귀 테스트로만 확인했다.

## 편집·승인 및 Blogger Mock 검토

기존 `BloggerWriter`는 `httpx.MockTransport`만 허용하고 이를 제공하지 않으면 `production_writes_disabled`로 차단한다. Fake publisher에는 실제 네트워크 클라이언트가 없다. 기존 테스트에서 초안 생성(POST), 기존 글 publish 및 예약, 같은 remote post ID를 대상으로 한 PATCH 수정과 DELETE, idempotency 중복 차단 및 불확실한 timeout 재시도 차단을 확인했다. 읽기는 별도 `BloggerReader`의 blog/post/list 경로에 유지된다. 로컬 `publishing_records`는 확인된 원격 게시글 ID와 원고 버전을 연결하며 Mock write ledger와 분리된다. Mock HTTP handler 테스트는 실 Blogger API 테스트나 실제 `publishing_records` 운영 매핑 검증으로 간주하지 않는다. 게시글 ID의 실서비스 생성·수정·삭제·예약 동기화는 승인과 비용 검토 전까지 미검증이다.

실제 OAuth 연결 행에는 `https://www.googleapis.com/auth/blogger.readonly` scope만 저장되어 있다. 추가 쓰기 권한 동의는 수행하지 않았다. Google Cloud 프로젝트 콘솔/결제 계정에는 접근하지 않았다. Blogger API 공식 사용 문서는 OAuth, 공개 데이터용 API key/OAuth 식별 및 API 동작을 설명하지만 검토한 문서에서 호출 단가나 무료 할당량을 명시하지 않는다. Google Cloud 문서는 API quota가 전체 지출 한도가 아니며 billing 상태는 프로젝트에 연결된 활성 계정을 확인해야 한다고 명시한다. 따라서 설정/요금 증빙이 완료될 때까지 `provider_cost_unverified`와 호출 차단을 유지한다. Google Blogger API 실요청은 이 Phase에서 전송하지 않았다.

공식 근거 (2026-10-27 확인): [Blogger API 사용 문서](https://developers.google.com/blogger/docs/3.0/using), [Google OAuth scope 목록](https://developers.google.com/identity/protocols/oauth2/scopes), [Cloud API 사용량 한도와 비용 안내](https://docs.cloud.google.com/apis/docs/capping-api-usage), [Cloud 프로젝트 결제 상태 확인](https://docs.cloud.google.com/billing/docs/how-to/verify-billing-enabled). Blogger API 문서에서 가격/무료 호출량 표시는 확인하지 못했고, Cloud Billing 연동 상태도 확인할 수 없었다.

## `apps/dashboard/AGENTS.md` 검토

파일은 프로젝트 `apps/dashboard` 하위에만 적용되는 Next.js 관리 안내 블록으로 구성되어 있다. `apps/dashboard/node_modules/next/dist/server/lib/generate-agent-files.js`에서 Next.js가 `next dev` 시 `AGENTS.md`를 쓰거나 관리 블록을 다시 추가한다는 근거를 확인했다. 파일은 실제 framework runtime에서 생성되었고, 루트 `AGENTS.md`의 보안·감사·브랜치·비용 정책을 약화하지 않는다. Next.js 문서 가이드 확인 규칙은 Dashboard 코드를 바꿀 때만 추가로 적용된다. 불필요한 파일로 판정할 근거가 없으므로 추적 상태를 유지했다.
