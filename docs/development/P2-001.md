## 구현 및 안전성

OAuth는 blogger.readonly 하나만 요청한다. state와 브라우저 바인딩은 해시, PKCE verifier와 Access/Refresh 토큰은 Fernet 암호문으로 저장한다. 토큰은 브라우저나 상태 API에 반환하지 않는다. 암호화 키·OAuth 비밀값은 Git 제외 설정에만 있다. 연결 해제는 로컬 토큰과 연결 검증을 지우며 과거 Blog ID·콘텐츠·감사·발행 이력은 보존한다.

Google getByUrl 응답의 ID와 URL을 확인하고 승인 계정의 AUTHOR 읽기 성공 후에만 연결을 저장한다. GET은 오류 분류·최대 3회 요청 예산·backoff/Retry-After, 401 강제 갱신 1회, 언어별 분당 제한을 적용한다. 요청 UUID와 안전한 오류·시도 정보만 감사한다. 쓰기는 MockTransport만 허용하며 실제 운영 쓰기 HTTP 경로를 노출하지 않는다. 모호한 쓰기 실패는 재전송하지 않고 DB 멱등성 원장으로 차단한다. AI 호출 차단과 자동 발행 false DB 제약을 유지했다.

로컬 콘텐츠 관리는 기존 그룹의 새 불변 버전을 생성하고 국가별 버전 번호를 advisory lock으로 직렬화한다. Blogger 초안을 생성하는 기능과 구분한다. 언어 등록에 따른 기본 실행 제한은 DB 트리거로 생성한다. 언어 수·실제 Blog ID를 코드에 고정하지 않았다.

## 포트와 실제 HTTP 검증

3100/8100 포트가 비어 있음을 소켓 및 Windows 상태로 먼저 확인했다. Next dev/start, FastAPI 실행, 서버 전용 API Base URL, 프록시 Host/Origin, Google redirect URI, 쿠키/콜백, 스모크 테스트, 환경 예제와 운영 문서를 함께 변경했다. 기존 비밀값·PostgreSQL 5432·다른 프로젝트 설정은 변경하지 않았다.

- 실제 Dashboard 3100 및 API 8100의 HTTP 200 확인.
- API 미인증 관리 요청 401, 외부/기존 3000 Origin의 프록시 요청 차단 확인.
- 브라우저는 same-origin BFF만 사용하며 FastAPI는 CORS 허용 헤더를 반환하지 않음.
- 잘못된 callback은 3100/blogger?oauth=failed로 303 이동하고 쿠키 삭제/no-referrer 적용.
- 별도 Mock OAuth 제공자로 실제 Next 3100 → API 8100 → callback 왕복 성공, HttpOnly 바인딩 쿠키, 일회용 state 및 replay 실패를 검증. 이 DB 변경은 모두 롤백함.
- HTML/상태 API에 관리자 bearer·Google 토큰·암호문이 없는지 확인.

## 검증 결과

- pytest 48개 통과, 경고 없음. 기존 httpx 사용 중단 예정 경고는 httpx2 개발 의존성으로 해결했다.
- OAuth 동의 거절·잘못된/만료/재사용 state, 잘못된 바인딩, 토큰 암호화·잘못된 키·만료 갱신·취소·scope 오류, API 401 갱신, 오류 분류, 제한·재시도·동적 언어·감사 검증.
- Mock Blogger 초안·발행·예약·수정·삭제, 같은 키 중복·다른 본문 충돌·모호한 네트워크 실패 재시도 차단 검증. 실운영 쓰기 테스트가 아님.
- PostgreSQL 001→006 보존 마이그레이션 및 재실행 통과. 기존 001–004 SQL은 변경하지 않았다.

- Python wheel은 새 소스 복사에서 격리 빌드해 테스트 harness와 비밀 파일 미포함 확인.
- Git 제외 파일과 실제 비밀값·암호화 키의 커밋 대상 제외 검사가 통과했다.

## 실제 Google 검증 구분

OAuth 클라이언트 설정은 발견했으나 사용자 Google 동의가 아직 없다. verify-blogger-live.py는 이 조건을 실제 읽기 미실행으로 명시하고 종료한다. 4개 실제 Blog ID를 만들거나 추정하지 않았다. 사용자에게 3100 콜백 URI의 Cloud 등록 및 /blogger 승인 절차를 안내했다. Google 계정 비밀번호를 요청·저장하지 않았다. 실제 4개 연결과 게시글 GET 성공은 후속 사용자 승인 뒤 검증해야 한다.

## 운영 잔여 과제 처리

격리 임시 DB를 생성해 원본 repeatable-read snapshot의 schema 6과 콘텐츠·감사·블로그·OAuth 테이블 건수, 감사 UPDATE 차단을 복원 검증했다. 임시 DB 이름·소유자를 확인한 뒤 해당 DB만 정리했다. 원본 DB는 복원 대상으로 사용하지 않았다. 복원 검증 성공은 운영 감사 이벤트로 기록했다.

현재 사용자 Interactive/Limited 권한의 Worker/Backup 작업을 등록했다. Worker의 실제 durable 작업 처리를 확인했고 Backup은 실제 백업 성공 및 LastTaskResult=0을 확인했다. 백업은 매일 03:00와 로그인 시 수행한다. 디스크 여유 약 13.7%가 기준 20% 미만이므로 로컬 대시보드·health.json·감사 이벤트에 경고한다. 성공한 백업을 경고만으로 재실행하지 않는다.

추가 검증에서 Worker가 0xC000013A로 중단된 상태를 발견했다. 이는 [Microsoft 문서의 CTRL+C 종료 코드](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55)이며 누가 신호를 보냈는지는 확인되지 않았다. 작업을 재시작해 큐의 이전 대기 작업과 새 진단 작업 완료를 확인했다. 실제 재부팅·로그아웃 무인 복구는 검증하지 않았다. 로그인 후 복구 절차를 운영 문서에 작성했다.

## 발견한 구현 문제와 해결

- httpx2 버전 범위 오지정으로 의존성 설치 실패: 실제 제공되는 2.x 범위로 수정 후 전체 테스트 경고 제거.
- 콘텐츠 SELECT FOR UPDATE의 최소 권한 충돌: 불필요한 UPDATE 권한을 주지 않고 advisory lock으로 버전 직렬화.
- 테스트 스크립트의 한글 파이프 인코딩 손상: UTF-8 읽기/쓰기와 안전한 검사 문자열로 수정 후 HTTP 재검증.
- 이전 build/lib 캐시가 wheel에 옛 테스트를 포함: 사용자 파일을 삭제하지 않고 소스 복사 격리 빌드와 woori 패키지 선택을 적용. 실제 wheel의 테스트/비밀 파일 미포함 확인.
- 백업 성공 시 디스크 경고가 작업 실패/재백업을 유발: 경고는 유지하되 실제 백업 실패만 비정상 종료하도록 수정.
