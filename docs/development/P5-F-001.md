## 수행 내용 및 증거

1. `scripts/status.ps1`와 Windows process/port 조회로 기존 PID·후손이 사라졌고 3100/8100이 비어 있음을 확인했다. 기존 llama.cpp PID 39500, 포트 11435, Qwen3 4B 모델은 그대로 두었다.
2. 운영 연결은 로컬 PostgreSQL 5432의 `woori_blog_agent`/`woori_owner`, runtime은 같은 DB의 `woori_app`임을 비밀정보 출력 없이 확인했다. 테스트 앱과 owner는 각자 `woori_blog_agent_test`에 연결하며 두 역할 모두 운영 DB CONNECT가 거부됐다. `scripts/provision-test-database.py`는 프로젝트 테스트 DB만 검증했고 schema 33, 격리 권한을 확인했다.
3. 신규 백업 `backups/20261027T065828Z.dump` (421,563 bytes, SHA-256 `19A6D571C9AC351EA5FD784B03FE218ACCF5E578CAAF04F3A8800E544ACB7CC0`)를 생성하고 PostgreSQL custom archive catalog 검증을 통과했다.
4. `.venv/Scripts/python scripts/restore-rehearsal.py`가 별도 임시 DB `woori_blog_agent_restore_20261027_d7959ae0`에 실제 복원했다. schema 32와 선택 테이블별 건수가 백업 스냅샷과 일치했고 감사 UPDATE 보호도 통과했다. 격리 DB 소유자·이름을 확인한 후 해당 임시 DB만 제거했다. 복원 산출물 `backups/woori_blog_agent_restore_20261027_d7959ae0.dump` (421,563 bytes, SHA-256 `BA0942E4DF7A2B026EC29D428D3B8994CEDFBF2B990E3490E6D654117369CFF0`)은 기존 백업 보존 정책에 따라 남겼다. 이 실행은 예상된 append-only `operations.restore.completed` 감사 이벤트 1건을 운영 DB에 추가했다.
